# d-map アーキテクチャ（Phase 2.2〜3.2）

## 構成

React → 同一オリジン `/api` → Flask → SQLAlchemy → SQLite。Viteの開発プロキシは5173→5000、テストは4173→5001。CORSでCookieを開放せず、プロキシは元のHostを保持する。本番は同一HTTPSオリジンのリバースプロキシ＋WSGIが必要。開発サーバーを本番用途にしない。

フロントはイベント全件取得を`eventService.fetchEvents`へ隔離。検索・ページネーション・地図の選択/ズーム制御は既存の構造を維持する。APIの成功空配列、通信失敗、取得中を分ける。初回成功後に地図を初期化し、更新時は同じ地図インスタンスを使用。サーバー認可済みの限定イベントだけをクライアント検索へ含める。クライアントの絞り込みは認可の代わりではない。

## 認証・認可

Flask-LoginのCookieにはユーザーID・セッション世代・CSRF用情報などが入り、生年月日やプロフィール自体は入れない。署名付きCookieは暗号化保管ではない。DBのsession_versionをログアウト時に更新し、既発行Cookieの再利用を拒否（同ユーザーの他端末もログアウトになる）。パスワードはWerkzeug scrypt、暗号方式を自作しない。

限定イベントは一覧、地図データ（同じ一覧API）、詳細、参加、統計すべてが同じ`visible_events`条件を使う。部外者には存在・住所・開催日時を返さず404。ログアウト/アカウント変更時にブラウザの限定データを破棄し、旧取得リクエストも中断する。URL直接指定の防御はサーバーで行う。

## トランザクション

SQLiteの1書き込みという性質を利用し、変更前に`BEGIN IMMEDIATE`で書き込み権を取得。ユーザー読込時の読み取りトランザクションを終了してから、認可・状態・定員・一意性を再確認して更新する。参加だけでなくイベント編集/削除や招待の失効/参加も同じ方式。定員変更と参加の競合も直列化される。外部キーON・複合主キーが追加の防御になる。

ロック待ちは15秒。取得できなければ503でロールバックし、参加成功を偽らない。SQLiteを別DBへ変更する場合は行ロック/条件付き更新等へ再設計する。同一ファイルに対する独立接続・独立プロセスのテストを行う。複数ホストのネットワーク共有DBや大規模負荷は未検証。

## プライバシー

年齢は本人の任意入力。生年と生年月日は排他的で、他者用プロフィールAPIは設けない。統計APIは対象者のID・名前・生年・生年月日・ハッシュ・メールを返さない。年齢/ジャンルそれぞれの同意と少人数抑制をサーバーで適用する。画面は取得時点のスナップショットで、「統計を更新」または参加変更後に再取得する。詳細はsecurity-checklistとAPI仕様を参照。

## 学習用の要点

Reactは操作と表示、Flaskは認証・認可・保存と整合性を担当する。ボタンを隠してもAPIは直接呼べるため、サーバーの認可が必須。DBの主キーは重複を防ぐが、複数人が最後の枠を同時に読む競合までは防げないため、ロックと一意制約の両方を使用する。
