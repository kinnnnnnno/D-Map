## UI-001：日時入力の操作性

| 項目             | 内容                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| 発見した課題     | ブラウザ標準の日付・時刻入力は環境により直接入力が必要になり、過去日の入力余地もある。                         |
| ユーザーへの影響 | 入力の負担、不正な条件による検索のやり直し、端末タイムゾーンに起因する日付ずれのリスク。実際の発生率は未測定。 |
| 改善前           | date/time入力。時刻は自由入力可能。形式チェック・区間重複検索はあるが過去日制限はない。検索ボタンで適用。      |
| 改善後           | カレンダーで日本時間の今日以降を選択。月・年送り。時刻は指定なし＋96個の15分刻み。条件変更を即時反映。         |

### 設計と理由

- `lib/calendar.ts` は年月日をタイムゾーンのない値として扱います。月末・うるう年は暦で計算し、検索時だけ明示的な `+09:00` の時刻へ変換します。`new Date('YYYY-MM-DD')` のローカル表示をカレンダーに使いません。
- `getTodayJst()` は `Intl.DateTimeFormat` の `Asia/Tokyo` から今日を取得。30秒ごとの確認、ウィンドウのフォーカス・表示状態変更時にも再確認します。日付変更から定期確認までの最大約30秒の間隔は残ります。
- 過去日はカレンダーボタンを無効化し、`validateSearchInput()` でも再確認します。2月30日・13月1日などのセルは生成しません。
- カレンダーは製品上の将来年上限を設けません。検索への変換はJavaScript Dateの表現可能範囲に依存し、範囲外はエラーとして扱います。
- カレンダーの矢印・Home/End・PageUp/Downによる移動、Enterによる選択、Escapeによる閉じる操作とフォーカス復帰を用意しました。選択日と今日の状態はARIA属性で伝えます。
- `SearchForm` の条件はAppが一元管理し、通常・拡大モードとも同じ関数で検索します。不正条件の間はエラーと0件を表示し、古い条件の結果を新しい入力の結果のように残しません。

### 日時区間の確定仕様

| 条件                 | 検索区間（JST、開始を含み終了を含まない） |
| -------------------- | ----------------------------------------- |
| 日付・時刻とも未指定 | 日時で絞り込まない                        |
| 日付のみ             | 当日00:00〜翌日00:00                      |
| 開始のみ             | 指定日・開始時刻〜翌日00:00               |
| 終了のみ             | 指定日00:00〜終了時刻                     |
| 開始より終了が早い   | 終了を翌日にする                          |
| 両時刻が同じ         | 入力エラー。24時間とは解釈しない          |
| 日付なし・時刻あり   | 入力エラー                                |

終了のみ00:00の指定は長さ0の区間になり、結果は0件です。重複判定 `eventStart < searchEnd && eventEnd > searchStart` はPhase 1から維持しました。検索ロジック自体は過去データの回帰テストにも利用するため、今日の制約は画面入力用の関数に分離しています。

### 追加テストと結果

- 単体：JSTの深夜0時・年越し、過去日・今日・明日、月末・年末、4/100/400年のうるう年規則、不正日付8例、年送り、10000年への移動、15分刻み96個、時刻の入力制約、既存の重複検索との一致を検証。成功。
- E2E：カレンダーのクリック・年/月送り、過去日のdisabled、うるう日、不正日のセル不在、時刻片側・深夜・同時刻エラー、条件即時反映、矢印/Enter/Escapeを検証。PC/モバイルの両設定で成功。
- 外部ユーザーによる操作負担の改善効果、実機のネイティブselectの使い勝手、スクリーンリーダーでの読み上げは未検証。

## UI-002：地図マーカーの誤認・重なり

| 項目             | 内容                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| 発見した課題     | ピンの番号が地域のイベント件数に見える可能性。同一座標は重なって存在を見落とすおそれ。                 |
| ユーザーへの影響 | ピンの意味を誤認する、隠れたイベントへ辿り着けない可能性。外部ユーザーによる誤認はまだ確認していない。 |
| 改善前           | 開催順の番号と共通の緑色。凡例なし。1イベントにつき1ピン。                                             |
| 改善後           | ジャンル別の色とB/H/P/L/他。凡例を常時表示。同一座標は「＋」付きピンから全件を選べる。                 |

### 設計と理由

`lib/markers.ts` の同じ定義をピン・凡例・一覧で共有し、不一致を防ぎます。

| ジャンル                  | 文字 | 色           |
| ------------------------- | ---- | ------------ |
| BREAK / BREAKING          | B    | 青 `#245a9b` |
| HIPHOP / HIP HOP          | H    | 茶 `#98500e` |
| POP                       | P    | 紫 `#74459a` |
| LOCK                      | L    | 緑 `#23644e` |
| HOUSE・WAACK・ALL STYLE等 | 他   | 灰 `#505b65` |

- 色だけに頼らず文字・ジャンル名・ピンのアクセシブル名でも識別できます。選択状態は輪郭線と一覧の「選択中」で示します。特定の色覚特性を持つ方による実地評価は未実施です。
- 座標をMapのキーにしてO(n)で集約します。座標をずらすSpiderfyより、元の開催位置を変えず全件を読める同地点一覧を採用しました。
- 複数のジャンルが同じ地点にある場合、未選択時は開催順で先頭のイベントの色と文字＋「＋」を表示します。選択後はそのイベントの色と文字に追従します。ポップアップでは各イベントのジャンル・日時・選択・詳細を表示します。
- 一覧と地図は同じ `selectedId` を参照。検索対象から外れた選択は解除し、検索結果だけをピンに渡します。非公開イベントは取得口・検索・集約で除外します。
- デモ件数は8件（公開7件）を維持。HOUSEイベントをHIP HOPイベントと同じ架空の渋谷会場へ移し、同地点の2件を再現できるようにしました。初期表示は公開7件・6地点です。
- LeafletのポップアップはDOMの `textContent` とテキストノードで構成し、イベント名・説明などをHTMLとして扱いません。

### 追加テストと結果

- 単体：ジャンル表記の対応9例、5分類の色・文字の区別、同地点集約、公開境界、絞り込み後の除外、0件、1000件の同地点データを欠落させないことを検証。成功。1000件の検証は性能ベンチマークではありません。
- E2E：実際の凡例とピンの文字・計算済み色の一致、番号廃止、同地点の2件の選択、一覧とピンの選択同期、選択ジャンルの追従、絞り込み後の他イベント・非公開イベントの除外を検証。成功。
- 今後：近接地点の重なり、広域・大量データのクラスタリングや描画削減、非常に多い同地点イベントの表示・DOM生成コストを改善する余地があります。現在は完全に同じ緯度経度だけを集約します。

## UI-003：地図の表示領域

| 項目             | 内容                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| 発見した課題     | 地図が固定された小さな領域で、位置関係を比較しにくい。                                                           |
| ユーザーへの影響 | 地図の移動・ズーム操作が増える可能性。比較しやすさの改善効果は未測定。                                           |
| 改善前           | 通常レイアウトのみ。地図の拡大モードなし。                                                                       |
| 改善後           | アプリ内でブラウザ表示領域いっぱいに拡大。PCは左に検索、モバイルは検索パネルを開閉。条件と選択を維持して戻れる。 |

### 設計と理由

- Fullscreen APIは使用せず、固定配置と `100dvh` で表示します。PCは上部ツールバー・左検索・右地図の構成です。狭い画面では上部の検索開閉ボタンから、最大高さ65%のスクロール可能なパネルを開きます。
- 画面モードで検索・地図コンポーネントを作り直しません。同じ状態を使うため、条件・選択イベントを維持します。拡大中は一覧を隠し、ピンの概要から詳細へ進めます。
- サイズ変更は `ResizeObserver` と切替後の `requestAnimationFrame` で `invalidateSize()` に伝えます。アニメーションなしで中心を保ち、通常表示・拡大・画面回転で地図を再配置します。
- 拡大中は背景をinertにし、Tabをワークスペース内で循環、背景スクロールを抑止します。Escapeで終了し、通常表示の拡大ボタンへフォーカスを戻します。カレンダー内の最初のEscapeはカレンダーだけを閉じます。

### 追加テストと結果

- E2E：表示領域の四辺、拡大中の日時・ジャンル変更、通常表示への復帰、条件・選択維持、サイズ変更後の地図四隅のタイル配置、中心位置の維持、Escape終了、フォーカス復帰、Tab循環、モバイルの検索開閉と横画面への変更を検証。成功。
- E2Eの初回実行で「拡大終了後のフォーカス復帰」がPC/モバイルの両方で失敗しました。モード変更時に起点ボタンが再生成され、古いDOM参照へフォーカスしていたことが原因です。復帰後のボタンを取得して修正し、同じテストで再発しないことを確認しました。
- 今後：実機のブラウザバー変化・ソフトキーボード・回転、VoiceOver/NVDA等での操作を確認する必要があります。

E2Eではタイルをローカルのテスト画像で応答し、フォント通信を止めています。ネットワーク状態で操作テストが不安定になることを避けるためです。**実際の地図画像の取得成功をE2Eで保証したものではありません。** 別のアプリ内ブラウザでOSM地図の実表示と操作を確認しました。

この実行環境では、制限内のesbuild実行が親ディレクトリの読み取り拒否で失敗したため、許可された実行で単体テスト・E2E・ビルドを行いました。製品コードの不具合による失敗とは区別しています。初回E2Eで検出したフォーカス不具合は上記UI-003に記録しました。

### ブラウザで別途確認した操作

- 実際の日本時間の今日と過去日の選択可否、10/24のカレンダー選択。
- 23:45〜翌00:15の深夜イベントが1件だけ表示されること。
- 地図拡大中のジャンル変更とピン更新、通常表示へ戻っても条件が残ること。
- 「＋」付きピンから渋谷の2件を確認し、HOUSEを選択すると一覧へ選択が反映されること。
- スマートフォン幅で検索パネルを開閉し、開始時間を変更してピンが1件になること。横方向のはみ出しなし。
- Escapeで通常表示へ戻れること、実際のOSMタイルと著作権表示。
