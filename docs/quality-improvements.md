`e2e/map-stability.spec.ts` に、短い停止を挟む連続移動・中心とサイズの更新、および既存Leafletのクラスなし連続パンの回帰テストを追加した。待機後の状態は自動待機なしで判定し、早すぎる終了を後続アサーションの待機で隠さない。

## UI-001：日時入力の操作性

| 項目             | 内容                                                                                                           |

| 発見した課題     | ブラウザ標準の日付・時刻入力は環境により直接入力が必要になり、過去日の入力余地もある。                         |
| ユーザーへの影響 | 入力の負担、不正な条件による検索のやり直し、端末タイムゾーンに起因する日付ずれのリスク。実際の発生率は未測定。 |

| 改善後           | カレンダーで日本時間の今日以降を選択。月・年送り。時刻は指定なし＋96個の15分刻み。条件変更を即時反映。         |

### 設計と理由

- `lib/calendar.ts` は年月日をタイムゾーンのない値として扱います。月末・うるう年は暦で計算し、検索時だけ明示的な `+09:00` の時刻へ変換します。`new Date('YYYY-MM-DD')` のローカル表示をカレンダーに使いません。
- `getTodayJst()` は `Intl.DateTimeFormat` の `Asia/Tokyo` から今日を取得。30秒ごとの確認、ウィンドウのフォーカス・表示状態変更時にも再確認します。日付変更から定期確認までの最大約30秒の間隔は残ります。
- 過去日はカレンダーボタンを無効化し、`validateSearchInput()` でも再確認します。2月30日・13月1日などのセルは生成しません。
- カレンダーは製品上の将来年上限を設けません。検索への変換はJavaScript Dateの表現可能範囲に依存し、範囲外はエラーとして扱います。
- カレンダーの矢印・Home/End・PageUp/Downによる移動、Enterによる選択、Escapeによる閉じる操作とフォーカス復帰を用意しました。選択日と今日の状態はARIA属性で伝えます。
- `SearchForm` の条件はAppが一元管理し、通常・拡大モードとも同じ関数で検索します。不正条件の間はエラーと0件を表示し、古い条件の結果を新しい入力の結果のように残しません。

### 日時区間の確定仕様

| 条件                 | 検索区間（JST、開始を含み終了を含まない） |
| -------------------- | ----------------------------------------- |
| 日付・時刻とも未指定 | 日時で絞り込まない                        |
| 日付のみ             | 当日00:00〜翌日00:00                      |
| 開始のみ             | 指定日・開始時刻〜翌日00:00               |
| 終了のみ             | 指定日00:00〜終了時刻                     |
| 開始より終了が早い   | 終了を翌日にする                          |
| 両時刻が同じ         | 入力エラー。24時間とは解釈しない          |
| 日付なし・時刻あり   | 入力エラー                                |

終了のみ00:00の指定は長さ0の区間になり、結果は0件です。重複判定 `eventStart < searchEnd && eventEnd > searchStart` はPhase 1から維持しました。検索ロジック自体は過去データの回帰テストにも利用するため、今日の制約は画面入力用の関数に分離しています。

### 設計と理由

`lib/markers.ts` の同じ定義をピン・凡例・一覧で共有し、不一致を防ぎます。

| ジャンル                  | 文字 | 色           |
| ------------------------- | ---- | ------------ |
| BREAK / BREAKING          | B    | 青 `#245a9b` |
| HIPHOP / HIP HOP          | H    | 茶 `#98500e` |
| POP                       | P    | 紫 `#74459a` |
| LOCK                      | L    | 緑 `#23644e` |
| HOUSE・WAACK・ALL STYLE等 | 他   | 灰 `#505b65` |

- 色だけに頼らず文字・ジャンル名・ピンのアクセシブル名でも識別できます。選択状態は輪郭線と一覧の「選択中」で示します。特定の色覚特性を持つ方による実地評価は未実施です。
- 座標をMapのキーにしてO(n)で集約します。座標をずらすSpiderfyより、元の開催位置を変えず全件を読める同地点一覧を採用しました。
- 複数のジャンルが同じ地点にある場合、未選択時は開催順で先頭のイベントの色と文字＋「＋」を表示します。選択後はそのイベントの色と文字に追従します。ポップアップでは各イベントのジャンル・日時・選択・詳細を表示します。
- 一覧と地図は同じ `selectedId` を参照。検索対象から外れた選択は解除し、検索結果だけをピンに渡します。非公開イベントは取得口・検索・集約で除外します。
- デモ件数は8件（公開7件）を維持。HOUSEイベントをHIP HOPイベントと同じ架空の渋谷会場へ移し、同地点の2件を再現できるようにしました。初期表示は公開7件・6地点です。
- LeafletのポップアップはDOMの `textContent` とテキストノードで構成し、イベント名・説明などをHTMLとして扱いません。

### 追加テストと結果

- 単体：ジャンル表記の対応9例、5分類の色・文字の区別、同地点集約、公開境界、絞り込み後の除外、0件、1000件の同地点データを欠落させないことを検証。成功。1000件の検証は性能ベンチマークではありません。
- E2E：実際の凡例とピンの文字・計算済み色の一致、番号廃止、同地点の2件の選択、一覧とピンの選択同期、選択ジャンルの追従、絞り込み後の他イベント・非公開イベントの除外を検証。成功。
- 今後：近接地点の重なり、広域・大量データのクラスタリングや描画削減、非常に多い同地点イベントの表示・DOM生成コストを改善する余地があります。現在は完全に同じ緯度経度だけを集約します。

### 設計と理由

- Fullscreen APIは使用せず、固定配置と `100dvh` で表示します。PCは上部ツールバー・左検索・右地図の構成です。狭い画面では上部の検索開閉ボタンから、最大高さ65%のスクロール可能なパネルを開きます。

- サイズ変更は `ResizeObserver` と切替後の `requestAnimationFrame` で `invalidateSize()` に伝えます。アニメーションなしで中心を保ち、通常表示・拡大・画面回転で地図を再配置します。
- 拡大中は背景をinertにし、Tabをワークスペース内で循環、背景スクロールを抑止します。Escapeで終了し、通常表示の拡大ボタンへフォーカスを戻します。カレンダー内の最初のEscapeはカレンダーだけを閉じます。

### UI-004：マーカーの密集

- **現象・影響**：Phase 1.1は完全に同じ座標だけを集約するため、近接する別座標のピンが重なり、イベントへ辿り着きにくくなる懸念がある。テスト用16件では、個別ピンのままでは近接10件が密集する条件を再現できる。一般の運用件数での発生率は未測定。
- **再現手順**：開発サーバーの `/e2e/fixtures/map-harness.html` を開く。同じ座標の5件、付近の10件、離れた1件があり、5ジャンルを含む。これらは通常のデモデータへ混ぜないテスト専用の架空イベント。
- **原因**：従来は緯度・経度の完全一致のみをキーにしており、ピンが画面上で占める大きさを考慮していなかった。
- **改善**：`clusterLocations()` にLeafletの投影座標を渡し、表示距離56px以内でつながる地点を集約。複数地点の丸い集約マーカーにはイベント件数と「イベント」の文字を表示し、凡例とアクセシブル名にも意味を明記する。同座標だけの地点はジャンル色・文字＋「＋」を維持。複数地点のグループは特定ジャンルの色にせず、ポップアップ内で各ジャンルを示す。
- **確認方法**：集約をクリック・タップすると全件の一覧が開き、個別の選択・詳細確認と「この範囲を拡大」が可能。最大ズームでも重なる地点は一覧から確認できる。ズームで構成が変わっても選択IDと一覧は維持し、検索対象外は除外する。
- **依存と設計理由**：ライブラリを追加せず、現在のLeaflet 1.9.4の公開API `project / zoomend / LayerGroup / Marker` を使用。UIから分離した小さな距離判定にしたため、Reactラッパーやプラグインの互換性・保守期限に依存しない。空間ハッシュで周辺セルを探索し、連鎖する近接地点もまとめる。同じ構成のマーカーは再利用し、概要DOMは開くときだけ作る。
- **追加テスト**：単体10件（件数保存、同座標5件、拡大相当の分離、混合ジャンル、絞り込み、0件、距離/セル境界、連鎖、安定キー、不正半径）。E2Eで近接15件すべてと遠方1件の詳細、同座標5件すべての選択、ジャンル対応、ズームと絞り込み・0件を確認。
- **開発中の検出事項**：概要内の選択時に遅延生成した内容を作り直す問題があり、開いている概要は再生成せず選択属性だけ更新する形へ修正。概要の最大高さも地図の実際の表示高に追従させた。
- **未解決・将来課題**：連鎖で広いグループになることがある。最悪時の近接探索はO(n²)。大量の異なる地点について性能保証はしていない。データ増加時にはSupercluster等の専用索引、表示範囲による間引き、概要のページ分割を別途評価する。地球一周・日付変更線付近のラップは今回の東京データでは未検証。

開発者本人から、検索解除の「ALL STYLE」が「FREESTYLE」や登録ジャンルの「ALL STYLE」と混同されるという追加要望があった。外部ユーザーテストの結果ではない。従来は検索解除を空文字、表示名をALL STYLE、登録ジャンルを「ALL STYLE（登録ジャンル）」としていたため、内部は別でも表示上の意味が分かりにくかった。

### 修正内容と設計判断

- 全件表示の名称を「すべてのジャンル」、内部値を専用の`all`へ変更した。
- `ALL_GENRES`定数と`GenreFilter`型を定義。検索条件だけが`all`または実ジャンルを持ち、イベントの`genre`には`all`を含めない。空文字や実ジャンルを検索解除の代わりに使わない。
- `filterEvents`は`genre === ALL_GENRES`のときだけジャンル判定を通過させる。他の日時・都道府県・種別・公開範囲の条件は解除しない。
- FREESTYLE、ALL STYLEの登録データと選択肢を維持。ALL STYLEの選択肢もその名称で表示し、個別選択時はそのジャンルだけを返す。
- 初期表示と検索リセットは共通の`emptyFilters.genre = all`を使う。UIでの変更値は既知のジャンルから取得し、型アサーションで任意の文字列を許可しない。
- 地図・イベント一覧・ページネーション・デモデータ・Flaskの実装、依存関係は変更していない。既存の未コミット変更を維持し、commit・pushは行わない。

### テストケース

- 既存のジャンル境界テストを更新し、初期値all、登録ALL STYLEはid7のみ、FREESTYLEはid12/16のみを確認。
- Vitest 2件追加：allがFREESTYLE・ALL STYLEを含む公開15件の全ジャンルを返し、groupを除外すること。allと複数県・日時を組み合わせた場合は11/1の8件となり、県条件を解除しないこと。
- 既存E2Eの空文字・旧表示名に対するアサートを新仕様に更新し、既存ケースは削除していない。
- Playwright 1シナリオ×PC/モバイル相当の2件追加：「すべてのジャンル」の名称と値、FREESTYLEの2件、ALL STYLEの1件、allへの復帰で15件、東京＋神奈川と11/1の併用で8件、FREESTYLE→allでも日時・県条件が維持されることを確認する。
- 日時は固定の基準2026-10-19 00:30 JSTから進める。E2EではOSMタイルをスタブし、外部通信に依存させない。

## UI-016：イベント登録時の開催場所指定（2026-10-23）

### 課題・影響・改善前

開発者本人から、緯度・経度を手入力するイベント登録・編集は一般利用者の負担になるとの改善要望があった。改善前は2つの数値入力に東京付近の既定値が入り、利用者が場所を選んでいなくても保存できた。外部ユーザーテストによる発見・改善効果の測定は実施していない。

### 改善内容・設計判断

- 通常フォームから座標の入力欄を撤去。`LocationPicker`専用のLeafletインスタンスを作り、検索画面の`EventMap`には変更を加えない。
- 新規作成では座標をnullとして開始。候補選択、地図クリック、地図中心の選択によって確定するまで理由を表示し、保存を無効化する。送信処理でも未確定・不正座標を検証する。
- 編集では既存座標を初期表示。マーカーのドラッグと東西南北への約50m調整が同じ内部状態を更新し、従来のイベントAPIのlatitude/longitudeに渡る。
- キーボードでは検索語入力→Enter→候補ボタン、または地図の矢印移動→中心選択→方向ボタンを使用できる。タッチでの地図選択にも対応。動きを減らす設定ではマーカーへの移動をアニメーションしない。

## BUG-024：日本式住所・番地検索（Phase 3.2.3）

### 発見した問題と再現手順

開発者本人の手動受け入れテストで、カンマ区切りでは候補が出る場合がある一方、一般的な日本式住所では候補を得られないと報告された。元の詳細住所は公開可否未確認のため非公開化した。公開用テストの例は `神奈川県架空市テスト区検証町７－８－９` で、これは元の実測住所ではない。架空住所を外部APIで検索した結果は未検証。候補がないことに加え、町丁目等の代表点を実際の会場と誤認して保存するリスクがある。外部ユーザーテストで発見したものではない。

### 調査と原因

調査開始時のGit作業ツリーはクリーン。既存の接続先は開発用公開Nominatim `/search` と `/reverse`。Reactはボタン操作で`POST /api/geocode`に元の住所を送り、Flaskは前後空白除去だけで`q`へ転送していた。全角数字・ハイフン・丁目/番/号の正規化も代替形式の検索もなかった。全候補をaccuracy=unknownとしており、サービスが返す地域レベルの違いも表示していなかった。

入力形式の問題とデータ/検索能力の限界は別である。NominatimはOSM由来の自由形式検索で、カンマは任意だが検索の複雑さを下げる（[公式Search仕様](https://nominatim.org/release-docs/latest/api/Search/)）。日本全国の番地・住居番号を網羅する保証はない。0件という応答だけでは「OSMにデータが一切ない」のか「検索索引/パーサーが一致しない」のか断定できない。実接続でも下記の番地検索は0件だったため、正規化だけで番地を特定できるとは判断していない。

### 改善前後・設計判断

- 改善前：生の検索語を1回送信、すべて精度不明。改善後：保存住所はそのまま、検索語だけを正規化し最大3形式まで探す。
- 全角ASCIIに限ってNFKCを適用し、日本語の互換文字・地名表記を全面的に書き換えない。数字に挟まれたハイフン/ダッシュ/長音を統一。漢数字は丁目の直前だけ、不要な日本語住所内空白と先頭郵便番号を処理。「センター」「一番町」「四日市」「京都」等の名前は別の地名に置換しない。
- 都道府県付きで末尾が明瞭な3数字区間の場合のみ、`7-8-9`→`7丁目8番9号`→番地を省いた`1丁目`（都道府県との間にカンマ）の順。候補があれば停止する。地番住所・建物名付き・4数字区間など曖昧な形式を推測で削らない。
- 同じボタン操作内の再検索だけ、共有ロック下で通信完了後1.1秒を待つ。最大3通信、各通信6秒、キャッシュ1時間/最大200エントリー。空結果もキャッシュする。新規の過密検索は429、外部429/タイムアウト/障害時の自動再試行なし。リクエストは入力中には送らない。
- 結果分類はaddresstype、建物分類ではhouse_numberも必要。関連度importanceやplace_rankを測量精度へ読み替えない。未知の種類は精度不明。番地を省いた再検索を番地・建物精度として返さない。
- UIは住所・都道府県・分類・注意を候補/選択地点に表示。建物分類でも番地一致や入口位置の保証ではない。低精度/不明候補も地図で利用者が確認し、明示的に確定する。
- 候補選択で中央表示、ピンのドラッグ/キーボード調整、解除、住所変更時の無効化、再確定、保存/編集/詳細の座標は既存の構造を維持。DBスキーマ・ユーザー/イベントデータは変更していない。

### 原因の切り分けと設計判断

- **A：外部サービス**は町丁目検索に対して町丁目の座標を返した。番地付き2形式は0件だった。サービスが対象番地データを保有しないことを、この結果だけで断定しない（検索索引/解釈も候補）。正解座標がなく、番地との距離・外部座標自体の地理的誤りは検証不可。
- **B：Flask**は番地検索0件から町丁目検索へ自動切替し、その代表位置を返していた。繰り返し同じピンになる経路を実測で再現した。キャッシュは同値入力で同じ応答を再利用するが、今回の初回地点の発生原因ではない。期限切れ後のサービス応答が変わるかは未測定。座標の加工・丸めはない。
- **C：React/Leaflet**は町丁目候補を1件なら自動プレビューし、ズーム17で中央へ移動していた。細かい倍率でも位置精度は上がらない。警告・townFallbackは表示されていたが、従来の確定判定は精度を条件にしておらず、町丁目候補を直接確定できた。これは安全上の欠陥。座標表示のずれはコード上見つからず、再生E2Eで照合する。ユーザーが当時見たピンと今回の座標が同じかは当時のログがなく未確認。

結論：**確認できたのはBのフォールバック＋Cの直接確定許可**。Aの返却座標が番地の座標でないことも確認したが、「外部が誤った番地座標を返した」「Leafletが座標を変えた」とは断定しない。
