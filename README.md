# d-map

**練習をもっとオープンに、つながりをもっと自由に。**

ダンサーが練習会・セッションを地図や日時から探し、グループ内では限定の練習予定を共有できるWebアプリです。ダンスバトルと比べて練習会の情報が分散し、見つけにくいという開発者本人の経験を起点に開発しました。

新卒QAエンジニア応募向けのポートフォリオとして、機能に加え、**操作で発見した課題→原因調査→改善設計→回帰テスト→結果と制約の記録**を重視しています。初期データは架空のデモイベント15件（東京13件・神奈川2件）です。ローカル学習用の実装で、本番サービスとしての公開準備は完了していません。

## 主な機能

- **イベント発見**：地図・日時の重複・ジャンル・種別・都道府県複数選択による検索。日付をまたぐ予定にも対応。
- **地図と一覧**：ジャンル別の色と文字、密集マーカーの集約、10件ページネーション、拡大表示。ページ変更では地図の中心・ズームを維持。
- **開催場所の登録**：住所検索、地図クリック、ピンドラッグ、キーボード調整。住所変更で古い座標を無効化し、位置確定後に保存。
- **認証・グループ**：登録・Cookieログイン・プロフィール編集・招待の期限/無効化・管理者権限・グループ限定イベント。
- **参加予定**：本人の参加/取消、定員、残り枠、飛び入り可否。実際の来場者数とは区別。
- **集計と操作性**：任意同意の年齢層・メインジャンル統計、少人数抑制。モーダルの背景スクロール禁止・フォーカス管理、レスポンシブ表示。

## 使用技術と構成

|領域|技術・役割|
|---|---|
|画面|React 19 / TypeScript / Vite / CSS|
|地図|Leaflet / OpenStreetMap。外部タイルの通信が必要|
|サーバー|Python / Flask / Flask-Login / Flask-WTF|
|DB|SQLite / Flask-SQLAlchemy / Flask-Migrate（Alembic）|
|検証|Vitest / pytest / Playwright / TypeScript / ESLint|

```text
ブラウザ（React・Leaflet）
  → 同一オリジン /api
  → Flask（認証・認可・入力検証）
  → SQLAlchemy → SQLite

住所検索ボタン → Flask → 設定されたNominatim互換サービス
```

開発時はVite 5173→Flask 5000、E2Eは専用の4173→5001です。画面の検索ロジックは純粋関数へ分離し、一覧と地図は同じ検索結果を使用します。認可はブラウザのフィルターではなくサーバーで行います。

## QA・品質改善の具体例

### BUG-027：ピンの位置ずれを処理経路ごとに切り分け

住所入力→正規化→検索クエリ→外部応答→キャッシュ→Flask JSON→React→Leafletを追跡しました。当時の対象住所では番地付き2形式が0件、町丁目へのフォールバックが1件で、`accuracy: town`・`townFallback: true`でした。返却座標とLeafletの座標は一致し、町丁目代表点が返る経路が位置精度不足につながっていました。サービス全体のデータ不足を証明したものではありません。

低精度・精度不明・番地を省略した検索候補は、そのまま位置確定できないようにしました。主催者が実際の会場を地図で照合し、手動指定してから再確定します。手動指定も位置の正しさを自動保証しません。

公開可否未確認の元住所・実測JSONはGit除外領域へ移し、公開用テストは完全な架空fixtureへ置換しました。**模擬応答の座標一致テストと、実住所の精度検証は別物**として記録しています。新しい架空住所の外部検索精度は未検証です。

### 参加定員：同時登録でも最後の枠を超えないか

SQLiteの`BEGIN IMMEDIATE`で書き込み権を取得してから、認可・開催状態・定員・二重参加を確認します。参加情報には複合主キーの一意制約も設けています。

pytestには、5つの独立接続が定員1/2へ同時に登録するテストと、2つの独立プロセスが最後の1枠を競うテストがあります。成功数・満員時の409・保存件数を検証します。複数ホストや大規模負荷の検証ではありません。

### 限定イベント：画面を隠すだけにしない認可

一覧・地図用データ・詳細・参加・統計で共通の可視範囲判定を使い、グループ外からの直接URL指定にも404を返します。公開イベントは作成者、限定イベントはグループ管理者だけが変更できます。

パスワードはWerkzeugのscryptでハッシュ化し、Cookie・CSRF・ログアウト失効を実装しています。生年月日等は本人以外へ返しません。統計は任意同意者だけを対象とし、5人未満または少人数セルがある場合はサーバーで内訳を抑制します。同意取消も検証対象です。

## ローカル起動（Windows PowerShell）

Node.js 22.12以上の対応LTSとPython 3.12以上を用意してください。Python仮想環境はプロジェクト専用の依存を分離します。

```powershell
# プロジェクト直下
npm.cmd install
cd backend
py -m venv .venv  # 既存環境があれば省略
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m flask --app app:create_app db upgrade
.\.venv\Scripts\python.exe -m flask --app app:create_app seed-demo
.\.venv\Scripts\python.exe -m flask --app app:create_app run --host 127.0.0.1 --port 5000
```

別ターミナルをプロジェクト直下で開き、`npm.cmd run dev`を実行して表示された5173番のURLへアクセスします。ホスト名は`127.0.0.1`に統一してください。既存DBを削除・初期化する必要はありません。デモ投入は既存IDを重複登録しません。

住所検索は任意です。未設定・障害時も地図から場所を指定できます。初回だけ、既存設定を上書きせず開発用設定例をコピーします。

```powershell
# backend内。公開サービスの利用条件を確認してから設定
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# 設定後はFlaskを再起動
```

接続設定は`backend/.env.example`の`GEOCODING_URL`・`GEOCODING_REVERSE_URL`・`GEOCODING_USER_AGENT`です。入力中の自動補完は行いません。検索・逆検索は明示操作、同一ホスト上の共有制限・キャッシュを利用します。個人宅・非公開住所は送信しないでください。本番では公開Nominatim接続を拒否します。[接続・通信制限](docs/development-history.md#開発用の接続設定)、[住所サービス比較](docs/geocoding-comparison.md)を参照してください。

Googleの評価CLIはアプリから分離され、既定はdry-runです。実測は未実施で、Google Mapsへの移行もしていません。APIキー・課金設定・利用上限確認が必要な手順は[評価資料](docs/google-geocoding-evaluation.md)に分けています。勝手に有効化せず、課金リスクを確認してください。

## テストの実行と結果

```powershell
# プロジェクト直下
backend\.venv\Scripts\python.exe backend/run_tests.py -q --tb=short
npm.cmd test
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build

# Edgeを利用。未導入の場合は npx.cmd playwright install chromium
$env:PLAYWRIGHT_CHANNEL='msedge'
npm.cmd run test:e2e -- --workers=1 --timeout=90000

# 不安定だった住所入力2ケースの反復検証
npm.cmd run test:e2e -- e2e/location-editor.spec.ts --grep 'BUG-027|UI-016 住所検索・候補' --repeat-each=3 --workers=1 --timeout=90000
```

E2Eは一時DBを使用し、通常の開発DBを使いません。認証・CSRFには実APIを通し、住所サービス・地図タイルはモックを使用します。通信・画面操作の回帰テストは、外部サービスの住所精度を保証しません。画像・トレース・レポートはGit除外対象です。

2026-10-28の今回の結果（Windows、Python 3.12、Node.js 24、Edge）：

|検証|結果|
|---|---|
|pytest全件|133成功・0失敗。既存の移行警告1件。初回のバックアップ誤収集を設定修正後に再実行|
|Vitest全件|155成功・0失敗|
|対象E2Eの反復・変更前|2ケース×PC/モバイル×3回＝12成功・0失敗|
|対象E2Eの反復・通信/描画の検証分離後|同条件で12成功・0失敗|
|型チェック・ESLint・ビルド|成功|
|全E2E・実機・外部API精度再測定|今回未実施|

対象E2Eは住所検索から保存・編集・詳細地図までのケースと、架空JSONのReact/Leaflet座標一致・低精度候補の直接確定禁止のケースです。検索POST応答200を確認してから描画を検証し、固定時間待機は追加していません。反復検証は部分実行で、過去の120件全体の成功とは数えません。[初回失敗を含む記録](docs/publication-preparation.md)を参照してください。

## 現在の課題と今後の改善

- 日本の番地・入口精度には限界があり、主催者の照合が必要です。ABR/Geolonia/Googleの比較は未測定項目を残しており、移行判断は保留です。
- 前回の住所E2Eは24/26成功、その後の対象4件は成功しました。今回の反復検証も成功しましたが、過去の通信待ちが長かった根本原因は未特定です。検索応答と描画を分けて検証できるようにし、未解決事項として記録しています。
- 実機スマートフォン、スクリーンリーダー、全ブラウザ、大規模負荷・侵入テスト・外部ユーザーテストは未実施です。
- メール認証、パスワード再設定、ログイン試行制限、監視・バックアップ運用等は未実装/未検証です。本番公開にはHTTPS・本番WSGI・秘密鍵管理を含む追加対応が必要です。
- ローカルGitには公開しない古いオブジェクトが残ります。mainだけの送信範囲と、コミット対象の再確認が必要です。

## 本人の担当範囲と生成AIの活用

開発者本人は、ダンスイベント検索の経験をもとに課題を設定し、必要な機能・期待する動作・改善の優先順位を検討しています。実際の画面操作による受け入れ確認を通じて不具合や操作上の課題を発見し、再現手順と期待動作を整理して改善につなげています。

生成AI（Codex）は、設計案の検討、実装、テストコードの作成、原因調査、ローカルでの自動テスト実行、ドキュメント整理を支援しています。実装・検証には生成AIの支援を活用し、本人による画面操作での確認と、自動テストによる検証を区別して記録しています。

QAの観点から、不具合が起きる条件と期待動作を明確にし、修正後は対象の動作と既存機能への影響を確認する進め方を重視しています。実施した検証・未実施の検証・残る課題を分けて記録し、外部ユーザーテストや未測定の改善効果を実績として扱わない方針です。
